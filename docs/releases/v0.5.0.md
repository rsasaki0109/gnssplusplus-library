# libgnss++ v0.5.0

This release adds a browser GUI: the libgnss++ command-line tools compiled
unchanged to WebAssembly behind an RTKLIB-style interface on GitHub Pages,
at <https://rsasaki0109.github.io/gnssplusplus-library/app/>. It also fixes
the empty `gnss fuse --kml` output, fused epochs missing from solution
statistics, and the FIX labels of `gnss fgo --preset real-data-fixed`. The
library/CPack/CMake package version is 0.5.0. The default behavior changes
are listed below.

## Highlights

- **Browser GUI (WebAssembly).** `gnss_convert`, `gnss_rinex_info`,
  `gnss_visibility`, `gnss_spp`, `gnss_solve`, `gnss_fuse`, `gnss_ppp` and
  `gnss_fgo` run in the browser with the same `main()` and options as the
  CLI. Files stay in the browser, and every run shows the equivalent
  `gnss ...` command. See the [guide](../web_app.md).
  - **Post-process**: SPP, kinematic / static / moving-base RTK, RTK + IMU
    (`gnss fuse`, tight coupling by default), batch FGO (experimental) and
    PPP. Settings can be saved and loaded as the `--config` TOML of
    `gnss solve`, `gnss fuse` and `gnss ppp`.
  - **Convert**: RTCM3 and u-blox UBX to RINEX.
  - **RINEX info**: header and record summary of RINEX files.
  - **Observations**: skyplot, one tracking row per satellite coloured by SNR
    or system with loss-of-lock slips, SNR vs elevation, and the satellite
    count.
  - **Plot**: RTKPLOT-style ground track and E/N/U or error vs a reference,
    with statistics. It adds OpenStreetMap or GSI map backgrounds, colouring
    by horizontal error, and PNG export.
  - *Keep files after reload* (opt-in) keeps the workspace in the browser's
    IndexedDB.
  - Results match the native tools: identical FIX/FLOAT status, and
    positions within 0.1 mm on the bundled sample and PPC Tokyo run1. The
    full Tokyo run1 RTK takes about 75 s in Chromium against 64 s natively.
  - CI builds the tools with Emscripten. It runs the demo pipeline in Node
    and drives the assembled site in headless Chromium before each
    deployment.
- **`gnss fuse --kml`** now draws the fused trajectory. Fused epochs carry
  no satellite count, and the KML writer used to drop all of them.
- **`gnss fgo --preset real-data-fixed`** on the Eigen batch path now reports
  per-epoch LAMBDA fixes. Before, the batch fix labelled every epoch FIXED.
  On PPC Tokyo run1's first 400 s, against the reference:

  | `real-data-fixed` | FIX epochs | Median 3D error | Over 0.5 m |
  | --- | --- | --- | --- |
  | v0.4.0 (batch label) | 2000 of 2000 | 0.98 m | 64 % |
  | v0.5.0 (per-epoch) | 22 | 0.03 m | 0 |

  Over the full run the per-epoch output fixes 138 epochs (1.2 %): median
  0.05 m, maximum 0.31 m.

## Default behavior changes

- `gnss fgo --preset real-data-fixed` without `--imu` on the Eigen backend
  turns on `--epoch-lambda-fixed-output` and `--report-batch-fix-as-float`.
  Long spans are much slower: 268 s for the full Tokyo run1 against 28 s for
  `real-data-float`. `--no-epoch-lambda-fixed-output` restores the v0.4.0
  output byte for byte. The GTSAM paths, the other presets and `FGOConfig`
  are unchanged. The summary JSON gains `report_batch_fix_as_float`.
- `Solution::calculateStatistics()`, `writeKML()` and `writeGeoJSON()` count
  every epoch that has a status and a finite position. This includes fused
  epochs with zero satellites; before, they required `isValid()` (at least
  4 satellites). GNSS-only output is unchanged on the data checked:
  `gnss solve`, `gnss fgo` and the `rtk_positioning` refactor gate on Tokyo
  run1 gave byte-identical results.
- `gnss convert --format rtcm` writes the first 1005/1006 station position to
  `APPROX POSITION XYZ`, as RTKLIB convbin does. A converted base log then
  solves without `--base-ecef`.
- `gnss visibility` without a RINEX header position uses the first valid SPP
  fix (or `--receiver-ecef`) instead of failing. It reports
  `receiver_position_source` and appends an `lli` column to its CSV.
- `gnss solve --config` accepts `base_ecef = [x, y, z]`.

## Get started

Open the browser GUI and press **Run demo pipeline**:
<https://rsasaki0109.github.io/gnssplusplus-library/app/>. Natively:

```sh
docker run --rm -v "$PWD/output:/workspace/output" \
  ghcr.io/rsasaki0109/gnssplusplus-library:v0.5.0 \
  demo --output-dir /workspace/output/self-contained-demo
```

The demo is an offline plumbing check, not a field-accuracy claim.

## Distribution

As in v0.4.0, release automation builds tag-matched TGZ/DEB packages for
Ubuntu 24.04 amd64, installs the DEB in a fresh container before publishing,
and attaches `SHA256SUMS`. The versioned GHCR image includes Python, NumPy and
Matplotlib. The browser GUI is published from `develop` by the Docs workflow.
See the [release runbook](../release_runbook.md).

## Accuracy and validation scope

The PPC Tokyo runs quoted here are development data, not holdouts. Ground
truth is used only for offline scoring. In the GUI, the batch FGO mode is
marked experimental. It is not more accurate than RTK on the PPC data checked
(see the [guide](../web_app.md)).
