# libgnss++ v0.6.0

> **Draft — not released yet.** The version bump (CMake project version,
> image references, release runbook and tests) is made when the release is
> cut.

This release separates real-time-equivalent from post-processing
positioning (`--realtime`), adds forward + backward post-processing for RTK
and PPP (`--combined`), and adds BeiDou PPP-B2b corrections and RINEX 4
modernized ephemerides. Several PPP fixes change the default results with
RTCM SSR and Galileo HAS, and the command-line tools now refuse malformed
input instead of running on it. The default behavior changes are listed
below.

## Highlights

- **Real-time equivalent mode: `--realtime`** for `gnss ppp`, `gnss spp`,
  `gnss solve` and `gnss replay`. A solution at epoch *t* uses only data a
  receiver could have had at *t*, so a recorded run gives the real-time
  result. See [Real-time and post-processing modes](../processing_modes.md).
  - SSR corrections: no sample after the epoch, no interpolation towards the
    next update, and no correction for a satellite before its first update.
  - SSR reception: an update applies from the time a receiver has it. HAS
    SIS and PPP-B2b use the reception of the completing page or message;
    RTCM SSR and MADOCA L6 take `--ssr-latency <s>`.
  - Broadcast ephemerides: a record is used only once broadcast. The RINEX
    reader keeps the transmission time of GPS, Galileo, QZSS and BeiDou
    records, and the RTCM decoders date each record by its reception.
  - RTK: no base interpolation towards the next base epoch and no guards
    that look at later epochs. `--base-hold-seconds <s>` holds the latest
    past base epoch.
  - Post-processed products (`--sp3`, `--clk`, `--ionex`) are refused.
  - The browser GUI has a *Real-time equivalent* checkbox in Post-process.
- **Forward + backward post-processing: `--combined`** for `gnss solve` and
  `gnss ppp`. A second filter runs the same epochs backward, and each epoch
  combines the two passes as RTKLIB's combined solution does.
  - On the six PPC Tokyo / Nagoya runs with the sign-off profile, FIX goes
    from 51.0 to 61.1 % of the reference epochs. Wrong FIXes stay at 0.96 %
    of FIX, and the distance-weighted PPC official score goes from 67.5 to
    72.3 %.
  - With PPP, the backward pass covers the forward filter's convergence: on
    the HAS SIS, PPP-B2b and JPL GDGPS static hours, H stays below 0.20 m
    from the first epoch. MADOCA PPP-AR on the MIZU sample goes from 91 to
    113 FIX of 118 epochs. On the OBE4 HAS IDD hour the result is worse.
  - The browser GUI has a *Forward + backward* checkbox for RTK and PPP.
- **BeiDou PPP-B2b corrections.** A decoder for the B2b-I messages of the
  BDS-3 GEO satellites, `gnss ppp --b2b <log>` (float PPP on GPS and BDS-3),
  the PPP-B2b choice in the GUI's PPP modes, and a `gnss reproduce
  bds-b2b-ppp` lane on the Kamakura hours. See [BeiDou
  PPP-B2b](../bds_ppp_b2b.md).
- **RINEX 4 modernized ephemerides.** GPS / QZSS CNAV and CNAV-2 and BeiDou
  B-CNAV1/2/3 records are read and evaluated, including the rate terms.
  They are kept apart from the legacy records, which every solver still
  uses unless asked otherwise.
- **More PPP corrections in the browser GUI.** QZSS MADOCA-PPP (L6E with
  optional L6D) and CLAS (experimental), Galileo HAS from the IDD (RTCM 3)
  or from logged E6-B pages, and PPP-B2b. Plot shows the PPP convergence
  against a reference point: error plots, the convergence time, and H / U
  at 10, 30 and 60 min.
- **PPP accuracy fixes.** H after one hour, static, before → after:

  | Run | Before | After |
  | --- | --- | --- |
  | HAS SIS, Kamakura 2025-02-15 | 0.184 m | 0.118 m |
  | HAS SIS, Kamakura 2025-08-21 | 0.520 m | 0.118 m |
  | JPL GDGPS RTCM SSR, Kamakura 2024-02-12 | 0.41 m | 0.029 m |
  | PPP-B2b, Kamakura 2025-02-15: time to stay below 0.2 m | 41.5 min | 15.8 min |

  The changes behind them:
  - IODE-matched RTCM SSR conversion by default.
  - A Galileo receiver clock with SSR.
  - The SSR URA weights the code only.
  - Expired held HAS / PPP-B2b corrections are no longer applied.
- **Robustness of the command-line tools.** Several failure modes that used
  to pass silently now stop with an error that names the option or file and
  the cause:
  - malformed numbers;
  - empty inputs;
  - unreadable RINEX epochs (these are skipped, with a warning);
  - products that do not load;
  - missing output directories (now created).

  Thirteen Python commands report a missing input file without a traceback.

## Default behavior changes

- **`gnss ppp --ssr-rtcm`** uses the IODE-matched conversion
  (`--ssr-rtcm-profile standard`) by default. `has-idd` remains an alias;
  `legacy` must be asked for.
- **PPP with RTCM SSR, HAS IDD or HAS SIS** estimates a Galileo receiver
  clock. The GPS L2 P(Y) / Z-tracked code (C2W) takes the L2 P / L2 W bias.
  - Results change on those paths: see the table above.
  - The OBE4 HAS IDD hour goes from 0.014 to 0.116 m static. Its earlier
    number relied on two errors offsetting each other.
- **The SSR URA weights the code only** (RTCM SSR, `--ssr` CSV, PPP-B2b).
  Coherent MADOCA and the CLAS OSR filter keep their reference weighting.
- **Held HAS and PPP-B2b corrections end with their validity**: a satellite
  is unused from the end of a hold until its next update, as in cssrlib.
- **`gnss ppp` stops when a requested product does not load** (ANTEX, BLQ,
  SP3, clock, SSR, IONEX, DCB, EOP, ATL), naming the file. Before, a partial
  SP3 / CLK load or a missing `--ssr` file could go unnoticed.
- **The RINEX reader skips an unreadable observation epoch** with a warning
  (file and line) and reads on. Before, reading stopped there.
  - A non-numeric observation value is read as missing.
  - An unreadable header line fails the header.
  - Valid files read as before: the PPC, PPP, MADOCA and CLAS outputs were
    byte-identical.
- **Numeric options must be whole, finite numbers** in `gnss solve`, `ppp`,
  `spp`, `fgo`, `fuse`, `replay`, `visibility`, `convert`, `live`, `stream`,
  `ubx-info`, `rtcm-encode` and `nav-products`. For example, `10deg`, `1x`,
  `nan` or a negative count are refused: `Error: invalid number for
  --ratio: abc`.
- **No data is an error.** These cases now exit 1:
  - `gnss spp` with no epochs, or no valid solution;
  - `gnss rinex-info` on a file that is not RINEX;
  - `gnss convert` when nothing was decoded;
  - `gnss ubx-info` with no UBX message.
- **Output directories are created** before processing by `gnss spp`, `ppp`,
  `fgo`, `fuse`, `solve`, `visibility`, `replay` and `convert`. An output
  path that cannot be written fails before the run.
- **`gnss ppp --ssr <raw L6>`** decodes natively only, without the Python
  subprocess it used to try first.
- **`gnss ppp --config`**:
  - `key = true` passes the flag of every option that is off by default;
  - the repeatable L6 options take arrays.

  Both example configs now run as written.

## Validation

- Each change that touched a solver compared the PPC Tokyo / Nagoya RTK runs
  and the PPP lanes before and after. The PPP lanes are HAS IDD, HAS SIS
  (two hours), PPP-B2b, JPL GDGPS (two hours), MADOCA and CLAS. Their
  default output moved only where listed above.
- On the release candidate, all of these give output byte-identical to the
  runs recorded when the last feature was checked. That covers the six PPC
  runs without and with `--combined`, the PPP lanes static and kinematic,
  and with `--combined`, and MADOCA with `--realtime --ssr-latency`.
- The `--realtime` / `--combined` changes were reviewed independently for
  time handling in both directions, for interactions between changes, and
  for the GUI against the CLI. The fixes are part of this release.

## Accuracy and validation scope

The PPC, Kamakura, OBE4 and MIZU data quoted here are development data, not
holdouts. Ground truth is used only for offline scoring. The cssrlib-data,
MADOCALIB and CLASLIB samples are checked out for tests only and never
redistributed.
