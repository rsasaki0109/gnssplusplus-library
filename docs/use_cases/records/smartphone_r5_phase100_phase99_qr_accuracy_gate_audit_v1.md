# Phase100 Phase99 QR accuracy-gate audit

- Execution label: `Luna Max`
- Audit date: `2026-09-03`
- Status: `sealed-read-only-audit-qualified-for-one-candidate-freeze`
- Scope: only the Phase99 structural-GO routes `2021-03-16-18-59-us-ca-mtv-a/pixel5` (MTV-A) and `2022-04-01-18-22-us-ca-lax-t/pixel5` (LAX-T).
- Question: whether one later accuracy evaluation can consume a fresh native
  Phase99 `MULTIFRONTAL_QR` solution from the raw-only pipeline under the
  already-sealed Phase82/43 metric contract, with truth kept evaluator-only.

This is a read-only contract audit. It did not open raw GNSS, IMU, or
navigation bytes; open a truth file; invoke the native solver; generate or
read a solution CSV; read MAT, base, or precomputed coordinates; calculate an
accuracy score; or access Kaggle/tokens. The companion freeze is a contract
only and authorizes neither raw execution nor accuracy evaluation.

## Decision

The sealed Phase99 structural result supplies exactly one candidate for a
future accuracy gate:

`phase100-phase99-main-multifrontal-qr-accuracy-v1`

The candidate is a new, one-run-per-route solution generated by the same
Phase99 raw-only QR command and recipe. The withheld Phase99 structural output
is not reused as the candidate. The candidate is not promoted by this audit.
The candidate must be compared with the exact immutable Phase43 control for
the same two route identities, using one evaluator process and the official
truth pins inherited from the sealed Phase82 cohort.

The route set is intentionally smaller than Phase82's four-route cohort.
Per-route scores and the macro score are comparable only when both sides of a
comparison use the same two route identities, parser, matching, and weighting.
The historical four-route Phase82 macro is therefore evidence for the metric
definition, not a numeric baseline for this two-route macro. The Phase82
MTV-H-specific gate and the Phase82-vs-Phase78 macro gate are not silently
applied: those route/cohort comparisons are outside this candidate's frozen
scope. The Phase82 strict numeric limits remain explicit AND gates below,
including the `0.782 m` macro limit, but the Phase100 two-route value must not
be described as directly comparable to the Phase82 four-route aggregate.

## Exact evaluation contract

The future evaluator must retain the Phase82 definitions exactly:

- Parse the candidate and Phase43 submissions with the CSV field order
  `phone,UnixTimeMillis,LatitudeDegrees,LongitudeDegrees`. Parse truth with
  `csv.DictReader` and required fields `UnixTimeMillis`, `LatitudeDegrees`,
  and `LongitudeDegrees`; optional truth columns are allowed. If a truth
  `phone` column is present it must equal the declared route; if absent, the
  declared route is assigned.
- The identity key is `(phone, UnixTimeMillis)`. Timestamps are exact integer
  keys; matching is exact key intersection only. Duplicate candidate or truth
  keys fail closed. A candidate key absent from truth fails closed.
- Candidate prediction-domain coverage is
  `matched prediction keys / prediction keys` and must equal exactly `1.0`.
  Truth-row coverage is informational, not a substitute for prediction
  coverage.
- Only the exact pinned leading warm-up truth key may be missing. No
  interpolation, nearest-neighbor matching, edge hold, extrapolation, or
  fill is permitted.
- Per-row error is spherical Haversine distance with Earth radius `6371008.8`
  metres. P50 and P95 use linear interpolation at rank `(n - 1) * q`.
  The route scalar is `(P50 + P95) / 2` in metres.
- The two-route macro is the unweighted arithmetic mean of the two route
  scalars, in fixed route order. A macro comparison is valid only for the
  same route set; no four-route Phase82 value may be mixed into it.
- Continuity uses Haversine transition speed from ordered prediction rows.
  `over_70_mps_count` must equal zero. Coordinates, distances, and all
  reported metric values must be finite and coordinates must be in valid
  Earth latitude/longitude ranges.

No new metric behavior, tolerance, Earth model, percentile method, weighting,
or matching rule is introduced by Phase100.

## Leakage and process boundary

The following are hard fail-closed conditions for the later evaluator:

1. Generate the two candidate solution CSVs first in a fresh, isolated output
   directory. The native process may receive only the Phase95-materialized
   `device_gnss.csv`, `device_imu.csv`, and broadcast `brdc.nav` paths, plus
   the pinned Phase99 route/config selectors. It may not receive a truth path,
   truth bytes, MAT file, base RINEX, PDC/WLS coordinate, precomputed
   coordinate, archive, token, or Kaggle path.
2. Validate candidate output schema, exact route/domain counts, key order,
   finiteness, and Earth ranges before any truth file is opened. The native
   process must have exited before evaluator truth access; no native process
   may be launched after truth access.
3. Resolve only the two official truth pins in the evaluator. Read each truth
   exactly once, after the future manifest and authorization, verify its
   sealed hash/byte/row metadata, and retain truth only in evaluator memory.
   Never expose truth paths, rows, coordinates, or scores to the native
   command or its summary.
4. Use one candidate run per route, no fallback, no solver rerun, no
   Cholesky comparison rerun, no post-truth tuning, and no score-based route
   selection. A failed predicate is a no-go; it cannot be repaired by
   interpolation, retry, alternate output, or threshold change.
5. Keep the candidate output private/temporary. Structural or accuracy GO
   does not authorize a solution publication, validation, or Kaggle submit.

The Phase43 controls are immutable evaluator-side references resolved through
the Phase82/Phase43 sealed identity pins. They are never passed to the native
solver and do not alter the fresh Phase99 candidate run.

## Strict promotion gates

Promotion is the conjunction of every gate below. The evaluator must record
each boolean and the exact route/macro values, but must not publish solution
rows.

| Gate | Required value |
|---|---|
| Candidate run count | exactly one fresh Phase99 QR run for each of MTV-A and LAX-T |
| Candidate route set | exactly the fixed two-route order; no MTV-H/U substitution |
| Candidate output integrity | exact header, expected rows, strict timestamp order, exact route keys, no duplicate/extra keys |
| Prediction-domain coverage | exactly `1.0` on each route |
| Candidate finite/Earth-valid | true for every evaluated row and derived metric |
| Continuity | `over_70_mps_count == 0` on each route |
| Per-route improvement | candidate route scalar is at least `0.05 m` lower than exact Phase43 control on both routes |
| No route regression | candidate route scalar is no greater than the same-route Phase43 control on either route |
| Macro improvement | two-route Phase43-control macro minus candidate macro is at least `0.1 m` |
| Absolute route limit | each candidate route scalar is at most `3.0 m` |
| Absolute macro limit | two-route candidate macro is at most `2.0 m` |
| Strict macro limit | two-route candidate macro is at most `0.782 m`; this is a declared Phase100 strict gate, not a four-route Phase82 comparison |

The Phase82 `MTV-H`-specific threshold and strict improvement against the
Phase78 four-route candidate are outside this frozen two-route scope. Adding
either comparator later would require a new freeze; neither may be inferred
from a passing or failing Phase100 result. No gate is a report-only target.
